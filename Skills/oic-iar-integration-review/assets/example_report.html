At a glance

The Fusion write works by conformance; everything around it is either broken or unused code.

The POST /timeEventRequests payload matches Oracle's schema and will create time events. But the employee validation call can never fail (the filter is put in the wrong part of the URL, so Fusion returns an unfiltered page of workers on every request), it runs even after validation already failed, nine of ten lookups feed variables nothing reads, and a "Success" reply is sent before Fusion has actually decided whether the punch becomes a time entry.

Architecture as built

A synchronous pass-through with a pre-check in front of it

IFS calls an OIC REST endpoint whose request contract is a copy of Fusion's timeEventRequests resource. OIC validates the first two time events, looks the employee up in Fusion, then forwards the caller's payload unchanged to Fusion and echoes Fusion's reply.

What works well

Keep these

The outbound payload conforms to Oracle's schema

All three required header fields (requestNumber, requestTimestamp, sourceId) and all three required event fields (eventDateTime, reporterId, reporterIdType) are mapped. timeEventAttributes[] carries name/value pairs exactly as the doc example shows. Resource path, verb and application/json media type are correct.

Shared, custodian-managed connections

CON061 is a common trigger connection and CON071 a single HCM connection with a parameterised URL — this is precisely what Oracle's "Too Many Connections" anti-pattern guidance asks for. TLS 1.2 is pinned.

The Fusion write is scoped with a fault handler

TimeRequestScope catches APIInvocationError, logs the error details to the activity stream, updates tracking variables and maps Fusion's errorDetails[] into the response instead of letting the instance die.

Sensible business intent

Pairing In/Out, requiring the same person and payroll time type on both punches, and allow-listing payroll time types are reasonable controls for a clock feed. The intent is right; the implementation is what needs work.

Primary tracking variable on the request number

Instances are searchable in Monitoring by IFS's requestNumber, which is the natural correlation key between the two systems.

Configuration was meant to be externalised

XX_OTL_CONFIG_LOOKUP holds source id, reporter id type, supplier device events, device id and default attribute per source system. The design intent — keep OTL constants out of the flow — is the right one; it just isn't wired in.

What a 201 actually means (Oracle OTL processing model)

Per Oracle's Time & Labor guides, the REST import "verifies the imported time events" and either returns inaccurately-formed resources in error, or "saves accurately formed resources to the time repository for further functional validations". Time entries are then created or completed by the scheduled Generate Time Cards from Time Collection Device process, which validates events against the Time Device Event Mappings and, for invalid events, creates time-entry exceptions for time and labor managers. A 201 therefore means accepted into the repository — not time entry created. The integration reports Success at the 201 and nothing ever reports the downstream outcome to IFS.

Oracle REST API for Fusion Cloud HCM · workers (GET)

Why the employee lookup returns everyone

Oracle documents two ways to find a worker on the collection: the q query parameter (PersonNumber is listed as a queryable attribute) or a finder. Both live in the query string. The integration instead declares a template (path) parameter and stuffs the whole query string into it.

As built (from GetEmpDetails_REQUEST.jca + map processor_1697)

// JCA endpoint definition
ResourceURI = /hcmRestApi/resources/11.13.18.05/workers/{QueryParam}
HttpVerb    = GET
// XSLT request map
<ns29:QueryParam>
  <xsl:value-of select="concat('?q=PersonNumber=', $PersonNumber)"/>
</ns29:QueryParam>
// Switch after the call
$GetEmpDetails/.../response-wrapper/count = 0.0   → "Employee Number not found"

As Oracle documents it

// Retrieve Past or Future Worker Details (Oracle example)
GET /hcmRestApi/resources/11.13.18.05/workers?q=PersonNumber='955160008191542'
// Querying a Collection (Oracle example)
GET /resources/11.13.18.05/workers?q=PersonNumber=1000
// Other documented query parameters
fields=PersonId,PersonNumber   // project only what you need
onlyData=true                  // drop link sections
limit=1                        // default page size otherwise applies
// Response semantics: "count" = items in the current range, not total

Consequence chain

1) OIC's REST adapter treats {QueryParam} as a path segment, not a query string — Oracle's adapter documentation keeps template parameters and query parameters as separate, separately-mapped constructs. 2) Fusion therefore never receives a recognised q filter, and the behaviour you observe — the default first page of the whole workers collection coming back — is the expected outcome of an unfiltered collection GET. 3) With no fields/onlyData/limit, each of those records is the full default worker representation. 4) count equals the number of items in the page, so count = 0.0 is never true on a populated tenant and the "Employee Number not found" branch is unreachable. 5) The response schema OIC generated from a hand-pasted sample only knows the top-level person fields, so the extra volume is parsed and thrown away.

Verify in one step: open any instance's activity stream and read ConnectivityProperties/RestAPI/http.target.endpoint.uri on the GetEmpDetails response (the adapter exposes it in RESTOUTRES). That is the literal URL Fusion received.

Decision first

One decision drives the design: who validates the punch?

Oracle already validates reporter identity, supplier event mapping and payroll time type when it processes time device events, and surfaces failures as exceptions in Time Management. The integration duplicates part of that in OIC (badly) and then throws away Oracle's answer. Pick one of the two models below; do not keep straddling them.

Model A — Fire-and-track (keep timeEventRequests)

Recommended when IFS is a real-time clock feed and Archrock relies on OTL time-device rules and event mappings
  1. Delete the worker lookup. Oracle's TCD import already "finds the person linked to the event" and raises badge/time-entry exceptions. A correct pre-check adds a second Fusion round-trip for no additional guarantee.
  2. Validate the whole payload in one JavaScript function (payload-in-JS): every timeEvents[] element, every attribute, ISO-8601 offset present, reporterIdType in Oracle's four values, supplierDeviceEvent in the configured set, payroll time type in the allow-list. Return one verdict code. This removes 30 Assigns and 3 Switches.
  3. Apply the DVM, or delete it. If XX_OTL_CONFIG_LOOKUP is meant to stamp sourceId, reporterIdType, supplierDeviceEvent and deviceId for the PXM source, map those values into the Fusion request. If IFS owns them, remove the seven lookups.
  4. Close the loop. Schedule Generate Time Cards from Time Collection Device at the agreed cadence and add a scheduled OIC job (BIP over the time-event exception data, or the Time Events REST resources) that reports rejected events back to IFS or to payroll. Change the IFS-facing status vocabulary to ACCEPTED rather than Success.
  5. Fault model: one scope per Fusion invoke with a handler; a global fault handler; return HTTP 4xx/5xx to IFS via Fault Return rather than 200 + "Error".

Model B — Synchronous time record (switch to timeRecordEventRequests)

Consider when IFS always sends a completed In/Out pair and payroll wants an immediate, authoritative yes/no
  1. Because the integration already insists on a paired In/Out for the same person and payroll time type, each request is really a time record (start, stop, attributes). Oracle's timeRecordEventRequests takes startTime/stopTime, reporterId/reporterIdType, timeRecordEventAttribute[] and a processMode (TIME_SAVE / TIME_SUBMIT).
  2. With processInline = "Y" Oracle processes the record in the call and returns eventStatus plus timeRecordEventMessage[] — validation outcomes come back in the same response IFS is waiting on. With "N" you must run Process Imported Time Entries.
  3. Trade-off (documented): this path bypasses time-device event mappings and time-device rules; it uses time-entry / submission rules instead. If Archrock's OTL configuration depends on TCD profiles, auto-generated Out events, or supplier-event exceptions, Model A is the correct one.
  4. Community reports (Customer Connect) show inline processing can return null timeRecordId and JBO errors on some records — prototype against Archrock's DEV pod before committing.
  5. Same JS validation, scope/fault and status-code discipline as Model A.
