# TypeScript in Next.js

> As of Next.js 16.3.8, verified 2026-10-04.

## Scope

This file owns the TypeScript layer of a Next.js App Router project: `tsconfig.json`, the Next.js
TypeScript plugin, `next-env.d.ts`, `next typegen`, typing `next.config.ts`, typed routes, the
route-aware helper types (`PageProps`, `LayoutProps`, `RouteContext`), typing async `params` and
`searchParams`, typing Server Actions and Route Handlers at the signature level, the general rule
for validating untrusted input, typing and validating environment variables, `server-only` and
`client-only`, and the TypeScript language rules agents apply (no `any`, `satisfies`,
discriminated unions, readonly data, `catch` variables as `unknown`).

It links out for everything else: [routing-and-metadata.md](routing-and-metadata.md) (metadata
objects, route files), [data-fetching-and-mutations.md](data-fetching-and-mutations.md) (Server
Actions and forms), [route-handlers-and-apis.md](route-handlers-and-apis.md) (handler design, status
codes), [proxy-auth-and-security.md](proxy-auth-and-security.md) (auth, secrets, public values),
[rendering-and-caching.md](rendering-and-caching.md) (caching, request-time rendering),
[testing-and-observability.md](testing-and-observability.md) (test setup) and
[nextjs.md](../nextjs.md) (principles, folder layout).

Rules are `TS-n` and snippets are `P1` to `P10`; every snippet is strict-mode TypeScript.

## Rules

### tsconfig and toolchain

1. **TS-1** Set `"strict": true` in `tsconfig.json` and never switch off a strict-family flag.
   `strict` enables `alwaysStrict`, `strictNullChecks`, `strictBindCallApply`,
   `strictBuiltinIteratorReturn`, `strictFunctionTypes`, `strictPropertyInitialization`,
   `noImplicitAny`, `noImplicitThis` and `useUnknownInCatchVariables`
   ([tsconfig reference](https://www.typescriptlang.org/tsconfig/)). TypeScript 6.0 makes `strict`
   default to `true`, so relying on the old `false` default now needs an explicit `"strict": false`
   ([TypeScript 6.0](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html)).
2. **TS-2** Add `noUncheckedIndexedAccess`, `noImplicitOverride` and `noFallthroughCasesInSwitch` on
   top of `strict`, because the strict family does not include them (convention).
   `noUncheckedIndexedAccess` adds `undefined` to any undeclared field in the type
   ([reference](https://www.typescriptlang.org/tsconfig/noUncheckedIndexedAccess.html)).
   `noImplicitOverride` requires the `override` keyword on overriding members, and
   `noFallthroughCasesInSwitch` requires a non-empty `case` to `break`, `return` or `throw`
   ([tsconfig reference](https://www.typescriptlang.org/tsconfig/)).
3. **TS-3** Keep `"plugins": [{ "name": "next" }]` in `compilerOptions` and, in VS Code, select "Use
   Workspace Version" so the Next.js TypeScript plugin runs. The plugin warns on invalid
   segment-config values, wrong `'use client'` usage and client hooks outside Client Components
   ([TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript)).
4. **TS-4** Keep `next-env.d.ts` and `.next/types/**/*.ts` in the `tsconfig.json` `include` array,
   add `next-env.d.ts` to `.gitignore`, never edit it, and put custom declarations in your own
   `.d.ts` file that `include` lists. Next.js manages `next-env.d.ts`, may change its contents, and
   overwrites edits ([TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript)).
5. **TS-5** Run `next typegen` before any standalone type-check, as in
   `next typegen && tsc --noEmit`, in CI and in the repo's types gate. `PageProps`, `LayoutProps`,
   `RouteContext`, the route types and `next-env.d.ts` are generated by `next dev`, `next build` or
   `next typegen`, so a bare `tsc --noEmit` does not validate route types. `next typegen` loads
   `next.config.*` in the production build phase, so give it the environment variables the config
   needs ([next CLI](https://nextjs.org/docs/app/api-reference/cli/next)).
6. **TS-6** Never set `typescript.ignoreBuildErrors: true`, and never point `typescript.tsconfigPath`
   at a relaxed build config (convention). `next build` fails on TypeScript errors, and
   `ignoreBuildErrors` skips the type-checking step, which the docs call very dangerous unless a
   type check runs elsewhere in the build or deploy
   ([TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript),
   [typescript option](https://nextjs.org/docs/app/api-reference/config/next-config-js/typescript)).
7. **TS-7** Write `next.config.ts` as `import type { NextConfig } from 'next'`, a
   `const nextConfig: NextConfig` and `export default nextConfig`. Module resolution in
   `next.config.ts` is limited to CommonJS; top-level `await` and dynamic `import()` work only
   through Node's native TypeScript resolver (Node.js 22.10.0 or later, on by default from 22.18.0),
   and CommonJS projects should name that file `next.config.mts`
   ([TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript)).
8. **TS-8** Enable `typedRoutes: true` at the top level of the config, not under `experimental`, and
   type `href` props with `Route` or `Route<T>` from `next`; cast `as Route` only for non-literal
   strings. The option is stable and requires TypeScript
   ([typedRoutes](https://nextjs.org/docs/app/api-reference/config/next-config-js/typedRoutes)).
   Literal and template-literal hrefs are validated for `next/link` and for `push`, `replace` and
   `prefetch` from `next/navigation`
   ([TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript)).
9. **TS-9** Map aliases with `paths` written relative to `tsconfig.json`, for example
   `"@/*": ["./src/*"]`, and set no `baseUrl` on TypeScript 6 or later. TypeScript 6.0 deprecates
   `baseUrl` as a look-up root, and TypeScript 7.0 removes the deprecated options
   ([TypeScript 6.0](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html)).
   With a `src/` folder the alias must include `src/`
   ([src folder](https://nextjs.org/docs/app/api-reference/file-conventions/src-folder)). The
   installation guide shows only `baseUrl`; do not copy it (see the last anti-pattern).
10. **TS-10** Use `import type` and `export type` for type-only imports and re-exports, and keep
    `"isolatedModules": true`, because Next.js compiles each file with SWC
    ([TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript)). A single-file
    transpiler cannot use type information, and re-exporting a type without `export type` is an
    error under the flag ([isolatedModules](https://www.typescriptlang.org/tsconfig/isolatedModules.html)).
11. **TS-11** Keep `typescript` at 5.1.0 or later and upgrade `@types/react` and `@types/react-dom`
    with every Next.js upgrade; on TypeScript 7 leave `experimental.useTypeScriptCli` at its
    default. Next.js 16 needs TypeScript 5.1.0 or later
    ([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16)), and async Server
    Components need TypeScript 5.1.3 or later with `@types/react` 18.2.8 or later
    ([TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript)). Opting out of the
    CLI checker with TypeScript 7 makes `next build` exit
    ([useTypeScriptCli](https://nextjs.org/docs/app/api-reference/config/next-config-js/useTypeScriptCli)).
12. **TS-12** Lint TypeScript with the ESLint CLI, using `eslint-config-next/core-web-vitals` plus
    `eslint-config-next/typescript` in `eslint.config.mjs`, and never call `next lint`
    ([ESLint](https://nextjs.org/docs/app/api-reference/config/eslint)). `next lint` is removed and
    `next build` no longer lints ([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16)).

### Route-aware types

13. **TS-13** Type every page with the global `PageProps<'/route'>` helper, passing the route literal
    exactly as its folder path with dynamic segments included, instead of a hand-written props type.
    The helper gives strongly typed `params` and `searchParams`, needs no import, resolves `params`
    to `{}` for static routes, and is generated by `next dev`, `next build` or `next typegen`
    ([page.js](https://nextjs.org/docs/app/api-reference/file-conventions/page)). See P4.
14. **TS-14** Type every layout with `LayoutProps<'/route'>` so `children` and each `@slot` folder
    arrive typed, and never hand-type parallel-route slot props. Slots are inferred from the
    directory structure, and a layout cannot read `searchParams`
    ([layout.js](https://nextjs.org/docs/app/api-reference/file-conventions/layout),
    [Next.js 15.5](https://nextjs.org/blog/next-15-5)). See P5.
15. **TS-15** Type every Route Handler's second argument with `RouteContext<'/route'>` and its first
    with `NextRequest` or `Request`. `context.params` is a promise since v15.0.0-RC
    ([route.js](https://nextjs.org/docs/app/api-reference/file-conventions/route)). See P6.
16. **TS-16** Treat `params` and `searchParams` as `Promise`s: `await` them in async Server
    Components and read them with React's `use()` in Client Components, and never read them
    synchronously. The hand-written type is `params: Promise<{ slug: string }>`
    ([page.js](https://nextjs.org/docs/app/api-reference/file-conventions/page)). Synchronous access
    is fully removed in Next.js 16 for `params`, `searchParams`, `cookies()`, `headers()` and
    `draftMode()` ([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16)).
17. **TS-17** Treat `searchParams` values as `string | string[] | undefined` read from a plain
    object, not a `URLSearchParams`, and validate them before use, because the client controls
    them ([page.js](https://nextjs.org/docs/app/api-reference/file-conventions/page)). Client input
    includes form data, URL parameters, headers and `searchParams`, and a folder with brackets is
    user input ([data security](https://nextjs.org/docs/app/guides/data-security)).
18. **TS-18** Annotate static metadata as `Metadata` and `generateMetadata` as returning `Metadata` or
    `Promise<Metadata>`, typing its `parent` argument as `ResolvingMetadata`; the detail lives in
    [routing-and-metadata.md](routing-and-metadata.md). The first argument may be typed with
    `PageProps<'/route'>` or `LayoutProps<'/route'>`
    ([generateMetadata](https://nextjs.org/docs/app/api-reference/functions/generate-metadata)).

### Untyped boundaries

19. **TS-19** Type every value that crosses a trust boundary as `unknown` and narrow it with a
    schema's `safeParse` before use: `request.json()`, `request.formData()`, Server Function
    arguments, `params`, `searchParams`, `process.env` and third-party JSON. Server Function
    arguments are fully client-controlled ([use server](https://react.dev/reference/rsc/use-server)),
    and client input must always be validated
    ([data security](https://nextjs.org/docs/app/guides/data-security)). `request.json()` resolves to
    anything JSON can represent and throws on invalid JSON
    ([Request.json()](https://developer.mozilla.org/en-US/docs/Web/API/Request/json)), and `formData`
    values are strings ([route.js](https://nextjs.org/docs/app/api-reference/file-conventions/route)).
    `safeParse` returns a success or failure object, while `parse` throws
    ([Zod basics](https://zod.dev/basics)); the forms guide validates with Zod or Valibot
    ([forms](https://nextjs.org/docs/app/guides/forms)).
20. **TS-20** Derive static types from schemas with `z.infer<typeof Schema>`, using `z.input` or
    `z.output` when a schema transforms, instead of writing a parallel interface (convention)
    ([Zod basics](https://zod.dev/basics)).
21. **TS-21** Check the repo's `zod` major before writing schemas; on Zod 4 use the `error` parameter
    instead of `invalid_type_error` and `required_error`, `z.flattenError()` or `z.treeifyError()`
    instead of `.flatten()` and `.format()`, and top-level formats such as `z.email()` and `z.url()`.
    Zod 4 also types the input of `z.coerce` as `unknown`, so a missing key under a `z.coerce.*`
    field fails unless you add `.default()` ([Zod 4 changelog](https://zod.dev/v4/changelog)).
    `z.flattenError()` returns `{ formErrors, fieldErrors }` ([error formatting](https://zod.dev/error-formatting)).
    The Next.js forms guide still shows `invalid_type_error` and `.flatten()`; do not copy them onto
    Zod 4 ([forms](https://nextjs.org/docs/app/guides/forms)).
22. **TS-22** Type each Server Action explicitly, as `(formData: FormData)` or, with `useActionState`,
    as `(prevState: State, formData: FormData): Promise<State>` where `State` is a discriminated
    union, and return only the minimal serializable data the UI needs; the detail lives in
    [data-fetching-and-mutations.md](data-fetching-and-mutations.md). The forms guide types the
    previous state `any`, which TS-28 forbids ([forms](https://nextjs.org/docs/app/guides/forms)).
    Return values are serialized and sent to the client, so constrain them to what the caller needs
    ([use server](https://nextjs.org/docs/app/api-reference/directives/use-server)). See P9.
23. **TS-23** Give Client Components props types that list only the fields they render, built from
    serializable values, never a full database-row type. Props passed to Client Components must be
    serializable by React
    ([Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)),
    and the data security guide calls an over-broad props interface bad
    ([data security](https://nextjs.org/docs/app/guides/data-security)).

### Environment variables and the server/client boundary

24. **TS-24** Read server env through one `server-only` module that `safeParse`s `process.env` against
    a schema and exports a readonly typed result, and report missing or invalid variable names only,
    never values (convention). Only the Data Access Layer should access `process.env`
    ([data security](https://nextjs.org/docs/app/guides/data-security)). Which values may be public
    is decided in [proxy-auth-and-security.md](proxy-auth-and-security.md). See P7.
25. **TS-25** Reference every browser-exposed variable with a literal `process.env.NEXT_PUBLIC_NAME`
    member expression, never `process.env[name]` and never a destructured or aliased `process.env`
    in client code, and treat the value as frozen at build. Next.js inlines `NEXT_PUBLIC_` values at
    build time, does not inline dynamic lookups, and the built app no longer responds to changes
    ([environment variables](https://nextjs.org/docs/app/guides/environment-variables)). See P8.
26. **TS-26** Treat `experimental.typedEnv` as editor IntelliSense only and never as validation. It is
    opt-in and generates types from the variables loaded at development runtime
    ([TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript)).
27. **TS-27** Put `import 'server-only'` at the top of every module that reads secrets, the database or
    server-only APIs, and `import 'client-only'` in modules that touch `window` or other
    browser-only APIs. A client import of a `server-only` module is a build-time error, and Next.js
    ships its own type declarations for both packages when `noUncheckedSideEffectImports` is active
    ([Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)).
    TypeScript 6.0 turns that flag on by default
    ([TypeScript 6.0](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html)).

### TypeScript language

28. **TS-28** Never write `any`, explicit or implicit: use `unknown` plus narrowing, a generic, or a
    precise type. The TypeScript handbook says not to use `any` outside a JavaScript-to-TypeScript
    migration, because it turns type checking off, and to prefer `unknown`
    ([do's and don'ts](https://www.typescriptlang.org/docs/handbook/declaration-files/do-s-and-don-ts.html)).
    An `unknown` value cannot be used until it is narrowed
    ([functions](https://www.typescriptlang.org/docs/handbook/2/functions.html)).
29. **TS-29** Use `satisfies` to check an object literal (a lookup table, route or plan map, or config
    record) against a type while keeping its narrow inferred type
    ([TypeScript 4.9](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html)).
    Keep annotating `next.config.ts` as `const nextConfig: NextConfig`, as TS-7 says. See P10.
30. **TS-30** Model variant results and UI states as discriminated unions on a literal field
    (`status`, `kind` or `ok`), and end every `switch` over them with a `never` exhaustiveness check
    ([narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html)). Zod models the
    same shape with `z.discriminatedUnion` ([Zod API](https://zod.dev/api)). See P9.
31. **TS-31** Declare data you pass around as `readonly` (`readonly` properties, `readonly T[]`,
    `as const` tables) and produce new objects instead of mutating (convention). `readonly`
    prevents re-assignment, not deep immutability, and is checked only at compile time
    ([object types](https://www.typescriptlang.org/docs/handbook/2/objects.html)); `as const` gives
    literal types ([everyday types](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html)).
32. **TS-32** Never use a type assertion (`as T`, non-null `!`) to stand in for validation; the only
    assertions allowed are `as const` and `as Route` on a computed `href` (convention). Assertions
    do no runtime checking
    ([everyday types](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html)). The
    environment variables guide's `process.env.DATABASE_URL!` is not a pattern to copy; validate
    through the module in TS-24 ([environment variables](https://nextjs.org/docs/app/guides/environment-variables)).
33. **TS-33** Suppress a compiler error only with `// @ts-expect-error <reason>` and never with
    `// @ts-ignore` (convention). `@ts-expect-error` reports an unused directive once the error is
    gone, while `@ts-ignore` stays silent
    ([TypeScript 3.9](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-9.html)).
34. **TS-34** Treat every `catch` variable as `unknown` and narrow it with `instanceof Error` before
    reading `.message`. `useUnknownInCatchVariables` is on under `strict`
    ([tsconfig reference](https://www.typescriptlang.org/tsconfig/)). The Route Handler reference's
    webhook example reads `error.message` on the catch variable, which does not compile under
    `strict` ([route.js](https://nextjs.org/docs/app/api-reference/file-conventions/route)).

## Patterns

### P1 tsconfig.json (TS-1, TS-2, TS-3, TS-4, TS-9, TS-10)

```json
{
  "compilerOptions": {
    "target": "ES2020",
    "lib": ["ES2020", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "moduleResolution": "bundler",
    "jsx": "react-jsx",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "isolatedModules": true,
    "esModuleInterop": true,
    "resolveJsonModule": true,
    "skipLibCheck": true,
    "allowJs": true,
    "forceConsistentCasingInFileNames": true,
    "noEmit": true,
    "incremental": true,
    "plugins": [{ "name": "next" }],
    "paths": { "@/*": ["./src/*"] }
  },
  "include": ["next-env.d.ts", ".next/types/**/*.ts", "**/*.ts", "**/*.tsx"],
  "exclude": ["node_modules"]

```

This is bmn's recommended file, not the `create-next-app` default. It starts from the compiler
options in the [Vite migration guide](https://nextjs.org/docs/app/guides/migrating/from-vite) and
adds the TS-2 flags and the TS-9 `paths`. Drop `src/` from `paths` when the repo has no `src` folder.

### P4 Page with PageProps and validated searchParams (TS-13, TS-16, TS-17, TS-19, TS-21)

```tsx
import { z } from 'zod'

const Query = z.object({
  q: z.string().max(100).optional(),
  page: z.coerce.number().int().min(1).default(1),
})

export default async function Page(props: PageProps<'/blog/[slug]'>) {
  const { slug } = await props.params
  const parsed = Query.safeParse(await props.searchParams)
  const { q, page } = parsed.success ? parsed.data : { q: undefined, page: 1 }
  return (
    <h1>
      {slug}: page {page} {q ? `(search: ${q})` : null}
    </h1>
  )
}
```

`?page=1&page=2` arrives as a `string[]`, which `z.coerce.number()` cannot turn into a number, so
`safeParse` fails and the fallback applies. A missing `page` takes the `.default(1)`.

### P5 Layout with a typed slot (TS-14)

```tsx
// app/dashboard/@analytics/ exists, so LayoutProps<'/dashboard'> types props.analytics.
export default function Layout(props: LayoutProps<'/dashboard'>) {
  return (
    <section>
      {props.children}
      {props.analytics}
    </section>
  )
}
```

Next.js 16 requires a `default.tsx` in every parallel-route slot
([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16)); slots are covered in
[routing-and-metadata.md](routing-and-metadata.md).

### P6 Route Handler with RouteContext and validated JSON (TS-15, TS-19, TS-21)

```ts
import type { NextRequest } from 'next/server'
import { z } from 'zod'

const Rename = z.object({ name: z.string().min(1).max(100) })

export async function PATCH(request: NextRequest, ctx: RouteContext<'/users/[id]'>) {
  const { id } = await ctx.params
  const body: unknown = await request.json().catch(() => null)
  const parsed = Rename.safeParse(body)
  if (!parsed.success) {
    return Response.json({ errors: z.flattenError(parsed.error).fieldErrors }, { status: 400 })
  }
  return Response.json({ id, name: parsed.data.name })
}
```

Status codes, authentication and error envelopes live in
[route-handlers-and-apis.md](route-handlers-and-apis.md).

### P7 Server env module (TS-24)

```ts
import 'server-only'
import { z } from 'zod'

const ServerEnvSchema = z.object({
  DATABASE_URL: z.url(),
  VERCEL_ENV: z.enum(['production', 'preview', 'development']).optional(),
})

export type ServerEnv = Readonly<z.infer<typeof ServerEnvSchema>>

export function readServerEnv(
  source: Readonly<Record<string, string | undefined>> = process.env,
): ServerEnv {
  const parsed = ServerEnvSchema.safeParse(source)
  if (!parsed.success) {
    const names = Object.keys(z.flattenError(parsed.error).fieldErrors).join(', ')
    throw new Error(`Invalid server environment variables: ${names}`)
  }
  return parsed.data
}
```

Save it as `src/lib/env.ts`. The error names the variables and never their values. `VERCEL_ENV` is
`production`, `preview` or `development`
([system environment variables](https://vercel.com/docs/environment-variables/system-environment-variables)).

### P8 Browser env (TS-25)

```ts
import { z } from 'zod'

const PublicEnvSchema = z.object({ NEXT_PUBLIC_ANALYTICS_ID: z.string().min(1) })

// Each variable is referenced literally so Next.js inlines it at build time.
export const publicEnv = PublicEnvSchema.parse({
  NEXT_PUBLIC_ANALYTICS_ID: process.env.NEXT_PUBLIC_ANALYTICS_ID,
})
```

`.parse()` throws a `ZodError` at module load when the value is missing
([Zod basics](https://zod.dev/basics)).

### P9 Server Action state as a discriminated union (TS-22, TS-30)

```ts
// app/signup-state.ts
export type SignupState =
  | { readonly status: 'idle' }
  | { readonly status: 'invalid'; readonly fieldErrors: { readonly email?: string[] } }
  | { readonly status: 'ok' }
```

```ts
// app/actions.ts
'use server'

import { z } from 'zod'
import type { SignupState } from '@/app/signup-state'

const Signup = z.object({ email: z.email() })

export async function signup(_prev: SignupState, formData: FormData): Promise<SignupState> {
  const parsed = Signup.safeParse({ email: formData.get('email') })
  if (!parsed.success) {
    return { status: 'invalid', fieldErrors: z.flattenError(parsed.error).fieldErrors }
  }
  // Authenticate, authorize and write through the server-only Data Access Layer here.
  return { status: 'ok' }
}
```

```tsx
// app/signup-message.tsx
import type { SignupState } from '@/app/signup-state'

export function SignupMessage({ state }: { state: SignupState }) {
  switch (state.status) {
    case 'idle':
      return null
    case 'invalid':
      return <p role="alert">{state.fieldErrors.email?.[0]}</p>
    case 'ok':
      return <p>Check your inbox.</p>
    default: {
      const _exhaustiveCheck: never = state
      return _exhaustiveCheck
    }
  }
}
```

The state type sits in its own module; whether a `'use server'` file may also export a type is
listed under Not confirmed by the docs. Wire the action with `useActionState`; see
[data-fetching-and-mutations.md](data-fetching-and-mutations.md).

### P10 satisfies with as const (TS-29, TS-31)

```ts
type Plan = 'free' | 'pro'

export const PLAN_LIMITS = {
  free: { projects: 3 },
  pro: { projects: 50 },
} as const satisfies Record<Plan, { readonly projects: number }>
```

## Anti-patterns

### Don't read params synchronously or hand-type page props (TS-13, TS-16)

Next.js 16 removed synchronous `params` access
([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16)).

**Don't**
```tsx
export default function Page({ params }: { params: { slug: string } }) {
  return <h1>{params.slug}</h1>
}
```

**Do**
```tsx
export default async function Page(props: PageProps<'/blog/[slug]'>) {
  const { slug } = await props.params
  return <h1>{slug}</h1>
}
```

### Don't cast request bodies to a type (TS-19, TS-32)

A cast does no runtime checking
([everyday types](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html)), and
`request.json()` can resolve to any JSON value or throw.

**Don't**
```ts
export async function POST(request: Request) {
  const user = (await request.json()) as { name: string }
  return Response.json({ name: user.name.trim() })
}
```

**Do**
```ts
import { z } from 'zod'

const User = z.object({ name: z.string().min(1).max(100) })

export async function POST(request: Request) {
  const body: unknown = await request.json().catch(() => null)
  const parsed = User.safeParse(body)
  if (!parsed.success) {
    return Response.json({ errors: z.flattenError(parsed.error).fieldErrors }, { status: 400 })
  }
  return Response.json({ name: parsed.data.name.trim() })
}
```

### Don't skip type errors in the build (TS-5, TS-6)

`ignoreBuildErrors` skips the type-checking step
([TypeScript](https://nextjs.org/docs/app/api-reference/config/typescript)). Fix the errors and run
`typecheck` in CI before the build.

**Don't**
```ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  typescript: { ignoreBuildErrors: true },
}

export default nextConfig
```

**Do**
```json
{
  "scripts": {
    "typecheck": "next typegen && tsc --noEmit"
  }
}
```

### Don't look up NEXT_PUBLIC_ variables dynamically (TS-25)

Dynamic lookups are not inlined, so the browser bundle never receives the value
([environment variables](https://nextjs.org/docs/app/guides/environment-variables)).

**Don't**
```ts
// Imported by a Client Component
export const analyticsId = (key: string) => process.env[`NEXT_PUBLIC_${key}`]
```

**Do**
```ts
// Imported by a Client Component
export const analyticsId: string | undefined = process.env.NEXT_PUBLIC_ANALYTICS_ID
```

### Don't read error.message on an untyped catch variable (TS-34)

The Route Handler reference's webhook example does this
([route.js](https://nextjs.org/docs/app/api-reference/file-conventions/route)); the catch variable is
`unknown` under `strict`.

**Don't**
```ts
export async function POST(request: Request) {
  try {
    await request.text()
  } catch (error) {
    return new Response(`Webhook error: ${error.message}`, { status: 400 })
  }
  return new Response('Success!', { status: 200 })
}
```

**Do**
```ts
export async function POST(request: Request) {
  try {
    await request.text()
  } catch (error) {
    const message = error instanceof Error ? error.message : 'Unknown error'
    return new Response(`Webhook error: ${message}`, { status: 400 })
  }
  return new Response('Success!', { status: 200 })
}
```

### Don't type a Server Action's state as any (TS-22, TS-28)

The forms guide types the `useActionState` first parameter as `any`
([forms](https://nextjs.org/docs/app/guides/forms)).

**Don't**
```ts
'use server'

export async function createUser(initialState: any, formData: FormData) {
  return { message: String(formData.get('email')) }
}
```

**Do**
```ts
'use server'

type CreateUserState = { readonly message: string }

export async function createUser(
  _prev: CreateUserState,
  formData: FormData,
): Promise<CreateUserState> {
  return { message: `Saved ${String(formData.get('email'))}` }
}
```

### Don't set baseUrl for path aliases on TypeScript 6 or later (TS-9)

The [installation guide](https://nextjs.org/docs/app/getting-started/installation) documents
`baseUrl`; [TypeScript 6.0](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html)
deprecates it.

**Don't**
```json
{
  "compilerOptions": {
    "baseUrl": "src/",
    "paths": { "@/components/*": ["components/*"] }
  }
}
```

**Do**
```json
{
  "compilerOptions": {
    "paths": { "@/components/*": ["./src/components/*"] }
  }
}
```

## Version notes

This file is verified against Next.js 16.3.8, the Active LTS release named in the
[September 2026 security release](https://nextjs.org/blog/september-2026-security-release).

- Next.js 16 removes synchronous access to `params` (page, layout, route, default and the image
  files), `searchParams`, `cookies()`, `headers()` and `draftMode()`. The codemod is
  `npx @next/codemod@canary next-async-request-api .`, and `npx next typegen` generates `PageProps`,
  `LayoutProps` and `RouteContext` for the migration
  ([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16),
  [Next.js 16](https://nextjs.org/blog/next-16)).
- Next.js 16 gives the image-generating functions (`opengraph-image`, `twitter-image`, `icon`,
  `apple-icon`) their `params` and `id` as promises, and `sitemap` its `id`
  ([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16)); see
  [routing-and-metadata.md](routing-and-metadata.md).
- Next.js 16 needs TypeScript 5.1.0 or later and Node.js 20.9 or later, removes `next lint` and the
  `eslint` config option, and defaults `@next/eslint-plugin-next` to flat config
  ([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16),
  [ESLint](https://nextjs.org/docs/app/api-reference/config/eslint)).
- Next.js 16 deprecates `revalidateTag(tag)` without a `cacheLife` profile; the guide says it "will
  produce a TypeScript error" ([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16));
  see [rendering-and-caching.md](rendering-and-caching.md).
- Next.js 16 removes `serverRuntimeConfig` and `publicRuntimeConfig`; use environment variables, as
  TS-24 and TS-25 describe ([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16)).
- Next.js 16 renames `middleware.ts` to `proxy.ts` with an exported `proxy` function
  ([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16)); see
  [proxy-auth-and-security.md](proxy-auth-and-security.md).
- Still current from 15.5: `typedRoutes` is stable at the top level and works with Turbopack, the
  route props helpers exist, and `next typegen` was added in 15.5.0
  ([Next.js 15.5](https://nextjs.org/blog/next-15-5),
  [typedRoutes](https://nextjs.org/docs/app/api-reference/config/next-config-js/typedRoutes),
  [next CLI](https://nextjs.org/docs/app/api-reference/cli/next)).
- Next.js 16.3 type-checks `next build` with the project-local `tsc` CLI by default, which enables
  TypeScript 7 while its JavaScript compiler API is unavailable; the checker covers the whole
  `tsconfig` project, tests included, and prints raw `tsc` diagnostics
  ([Next.js 16.3](https://nextjs.org/blog/next-16-3),
  [useTypeScriptCli](https://nextjs.org/docs/app/api-reference/config/next-config-js/useTypeScriptCli)).

## Review checklist

- [ ] `tsconfig.json` has `"strict": true` and no strict-family flag turned off (TS-1)
- [ ] `noUncheckedIndexedAccess`, `noImplicitOverride` and `noFallthroughCasesInSwitch` are on (TS-2)
- [ ] `next-env.d.ts` is gitignored, unedited and in `include` (TS-4)
- [ ] The type gate runs `next typegen` before `tsc --noEmit` (TS-5)
- [ ] No `ignoreBuildErrors: true` and no relaxed `tsconfigPath` (TS-6)
- [ ] `next.config.ts` is typed with `NextConfig` (TS-7)
- [ ] `typedRoutes` is on, and `as Route` appears only on computed hrefs (TS-8, TS-32)
- [ ] No `baseUrl` on TypeScript 6 or later (TS-9)
- [ ] Pages, layouts and handlers use `PageProps`, `LayoutProps` and `RouteContext` (TS-13, TS-14, TS-15)
- [ ] `params` and `searchParams` are awaited, never read synchronously (TS-16)
- [ ] Every boundary value is `unknown` and goes through `safeParse` (TS-17, TS-19)
- [ ] The Zod API matches the installed major version (TS-21)
- [ ] Server Action signatures and state are typed, with no `any` (TS-22)
- [ ] Client Component props are minimal and serializable (TS-23)
- [ ] Server env is read through a validated `server-only` module that reports names only (TS-24)
- [ ] `NEXT_PUBLIC_` variables are read as literal `process.env.NEXT_PUBLIC_NAME` (TS-25)
- [ ] Modules that touch secrets import `server-only` (TS-27)
- [ ] No `any` and no `@ts-ignore` (TS-28, TS-33)
- [ ] Unions end in a `never` check (TS-30)
- [ ] Every `catch` narrows with `instanceof Error` (TS-34)
