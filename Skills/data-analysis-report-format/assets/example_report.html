Section 04

Structural-validation observations

Findings mapped to the HDL structural-validation rules — each is a hard load failure independent of field completeness.

Rule 11

No HIRE records in this sample

Every ActionCode is ASG_CHANGE, INVOLUNTARY_TERMINATION, or RESIGNATION. Zero records carry ActionCode = HIRE or ADD_CWK. Under HDL rules the first assignment row for every person must be a HIRE (or ADD_CWK for contingent). If this extract loads as-is, all 40 persons fail because no person's history opens with a HIRE action — the single most consequential structural finding. Most likely explanation: these are delta / change rows from a live Fusion system, with HIRE records in a separate historical file or a prior conversion. The engagement question is whether this file loads on top of an already-resident population or stands alone — that answer determines whether the missing HIRE records are a gap or by design.

Rule 16

WorkerType / AssignmentType / SystemPersonType triad

WorkerType is blank for all 40 records. HDL requires a valid triad — WorkerType E + AssignmentType E + SystemPersonType EMP for employees. Without WorkerType the triad cannot be formed and the load rejects. A hard reject for every record as currently structured.

Rule 2 / 13

Date format

All EffectiveStartDate values are formatted YYYY-MM-DD (hyphens). HDL requires YYYY/MM/DD (slashes). A universal transformation gap — every date column must be reformatted before load, with silent-corruption risk if the loader misinterprets the delimiter.

Rule 25

EffectiveSequence / EffectiveLatestChange absent

Assignment Sequence is blank for all 40 records. For any person with multiple transactions on the same effective date — and given the 2026-01-01 cluster, co-incident transactions are likely — EffectiveSequence must increment and EffectiveLatestChange must be Y on the last same-day record and N on prior ones. No sequencing data is present.

Rule 15

INACTIVE_PROCESS on a termination (PersonNumber 10631)

PersonNumber 10631 carries ActionCode = INVOLUNTARY_TERMINATION (facility closure) with AssignmentStatusTypeCode = INACTIVE_PROCESS. Rule 15 expects termination rows to carry an INACTIVE status — the standard being INACTIVE_NO_PROCESS. INACTIVE_PROCESS on a termination is atypical and will either reject or trigger an unexpected workflow, depending on configuration. Requires explicit validation against IP's configured status mapping.

Rule 9

Lookup value Conversion on HourlySalariedCode (terminated records)

All 20 terminated records carry HourlySalariedCode = Conversion (mixed case). The configured lookup values are H (Hourly) and S (Salaried); Conversion is not a standard Fusion lookup. If these records are re-loaded or used as a template, this value will reject unless a custom lookup is configured.

Rule 18

Foundation FK validation unverifiable for CONVERSION placeholders

The 20 terminated records reference LocationCode / DepartmentName / GradeCode / JobCode = CONVERSION — literal strings, not real workforce-structure references. If terminated records must be re-loaded, none of these FKs resolve to real foundation objects. Decision required on terminated-population scope (see Open Decisions).

Rule 18

PositionCode .0 suffix

Active records carry PositionCode values like 30001158.0 — an Excel numeric-to-float artifact. Fusion position codes are strings; the .0 suffix causes FK match failures against the position master unless stripped in the transformation layer.

Structural gap

No manager reference column

The extract contains no manager identifier (no LineManagerPersonNumber, ManagerPersonNumber, or equivalent). The manager hierarchy cannot be loaded from this file — a structural gap, not a data-quality gap. A separate manager-hierarchy extract is a required input.

Operating-model inference

Inferred from the sample — flag any that are incorrect.

Single legal employer, US-only

International Paper Company is the sole legal employer in this sample. All location codes are US state–prefixed, implying a single legislation (US) and a single Legislative Data Group, though multi-state payroll-tax complexity is visible from the geographic spread.

Position management is active

Every active worker carries a numeric PositionCode, and PositionOverrideFlag = Y on all active records suggests positions are in use but individual assignment attributes can be overridden — a common IP pattern where position controls the default but workers may carry different grades or hours.

Facility-based org structure

Department names follow {Facility Name} - {Function} - {Number} (e.g., Reading Box - Production - 167036). Functions visible: Production, Maintenance, Overhead, Shipping. The trailing numeric (167xxx, 250xxx) is likely a legacy cost-center / org-unit identifier — a useful join key if a separate org extract exists.

Terminated population loaded with CONVERSION placeholders

The 20 terminated records carry no real position, department, location, grade, or job data — a deliberate choice from the prior conversion to record the termination event, not the full org footprint. No terminated worker here can be used to reconstruct their last-active org assignment.

Substantial custom action-reason vocabulary

The IP_Z* reason codes (IP_ZA_15_FOR_CAUSE_ATTENDANCE, IP_ZA_5_FACILITY_CLOSURE, IP_ZA_12_REDUCTION_IN_FORCE, IP_ZA_8_RESIGNATION, IP_ZB_1_RETIREMENT, …) indicate a custom action-reason library that must be configured before any referencing load. Retirement (IP_ZB_1_RETIREMENT) carried on an ActionCode = RESIGNATION row (PersonNumber 10484) suggests the action was mapped to RESIGNATION rather than a distinct RETIREMENT action — intentional, or an action-mapping gap.

Custom LOA assignment status types

IP_LOA_WITHOUT_PAY and IP_LOA_WITH_PAY are client-specific assignment status type codes that must exist in Fusion's assignment-status configuration before the two LOA workers can load.

Section 07

Open decisions & missing data

Design decisions this sample raises.

  1. Terminated-population scope & re-load strategy. Are the 20 terminated workers in scope for conversion / re-conversion? If yes: what org data do they carry at termination — the CONVERSION placeholders cannot be used as real FK references, so either real last-active org data is sourced separately, or terminated workers continue to load with placeholders and a formal limitation is accepted. If no: only the 20 active/LOA workers are in scope. The largest scoping lever visible in this sample.
  2. History vs. as-of-go-live. The absence of HIRE records raises whether this is a history/delta file loading on top of existing person records, or a go-live snapshot that should include HIRE rows. Clarify the load context before building the transformation.
  3. INACTIVE_PROCESS status mapping. Is INACTIVE_PROCESS intentional for the facility-closure termination (PersonNumber 10631), or should it align with INACTIVE_NO_PROCESS per standard termination mapping? Confirm with IP's HR configuration team.
  4. Position override strategy. PositionOverrideFlag = Y for all active workers implies assignment-level attributes can differ from position defaults. Confirm which fields IP overrides at the assignment level vs. inherits from the position — this drives the HDL transformation rules.
  5. Grade structure scope. Grade codes embed facility and union designation (e.g., USPA76-USW 1419-09). The full population likely has many distinct grade codes. Confirm whether grades are a flat per-facility lookup or a grade-ladder / grade-step structure (GradeLadderPgmName and SpecialCeilingStep are present but blank here).
